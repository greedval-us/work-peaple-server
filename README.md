# Work People — сервер

NestJS + TypeScript, gRPC, PostgreSQL 18, Redis 8. Один сервер обслуживает одну
компанию с несколькими отделами. Сейчас реализован технический каркас и проверка
состояния; авторизация и операции над сотрудниками ещё не реализованы.

## Требования

- На удалённом хосте `192.168.0.102`: Docker Engine с Compose v2.
- Node.js 24 LTS и npm на удалённом хосте нужны только для разработки исходников
  с автоматическим перезапуском. Развёртывание и проверки выполняются в Docker.
- На Windows: SSH-клиент для доступа к хосту и туннеля к API.
- Соседний клиентский репозиторий не нужен для сборки сервера.

Пользователь `greed` запускает Docker через `sudo`; команды ниже учитывают это.

API, PostgreSQL, Redis, миграции и серверные интеграционные тесты запускаются
только на `192.168.0.102`. На локальном Windows выполняются разработка и сборка
Electron-клиента; серверные компоненты там не запускаются.

## Запуск в Docker на удалённом хосте

Откройте SSH-сеанс из PowerShell под учётной записью `greed`;
стандартный порт SSH — 22:

```powershell
ssh -i "$HOME/.ssh/id_ed25519_hostkey" -p 22 greed@192.168.0.102
```

`-i` выбирает существующий локальный ключ `~/.ssh/id_ed25519_hostkey`;
приватный ключ не переносится на сервер.
Если ключ не принят, SSH запросит пароль интерактивно; пароль не сохраняется в проекте.
Разместите актуальный серверный репозиторий на удалённом хосте. Все команды
в следующем блоке выполняйте в открытом SSH-сеансе, из его папки репозитория:

```sh
cd /home/greed/apps/work-people-server
# Только при первом запуске. В проверенном развёртывании .env уже создан.
# Не заменяйте существующий .env при обновлении исходников.
test -f .env || cp .env.example .env
# Задайте уникальные POSTGRES_PASSWORD и REDIS_PASSWORD в .env.
# Согласуйте с ними DATABASE_URL и REDIS_URL для команд на удалённом хосте.
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose logs -f api
```

Пароли в Compose подставляются в URL: используйте буквы, цифры, `-` и `_`.
Не оставляйте примерные пароли при развёртывании. Сгенерировать подходящий пароль
можно в контейнере из того же SSH-сеанса:

```sh
sudo docker run --rm node:24-bookworm-slim node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Compose собирает непривилегированный runtime-образ, ждёт готовности PostgreSQL,
применяет миграции отдельным сервисом и запускает API. PostgreSQL и Redis находятся
во внутренней сети; gRPC опубликован на `127.0.0.1:50051` удалённого хоста.
Оставьте `GRPC_BIND_ADDRESS=127.0.0.1` для доступа через SSH-туннель. Данные хранятся в
именованных томах. `sudo docker compose down` сохраняет данные; флаг `--volumes` удаляет их.

Проверить всю цепочку API → PostgreSQL/Redis в том же SSH-сеансе:

```sh
sudo docker compose exec api node scripts/healthcheck.mjs
```

## Подключение Windows-клиента

В отдельном PowerShell на Windows откройте туннель и оставьте его работающим:

```powershell
ssh -i "$HOME/.ssh/id_ed25519_hostkey" -p 22 -N -L 127.0.0.1:50051:127.0.0.1:50051 greed@192.168.0.102
```

Клиент сохраняет `GRPC_TARGET=127.0.0.1:50051` и `GRPC_TLS_ENABLED=false`.
SSH шифрует передачу до удалённого хоста; Compose продолжает публиковать gRPC
только на его loopback. Запустите Electron по инструкции клиентского репозитория.

## Разработка и проверки сервера по SSH

Следующие команды выполняются только на `192.168.0.102`, в SSH-сеансе из папки
серверного репозитория. Рекомендуемая проверка сервера выполняется в контейнере:

```sh
sudo docker build --target verify -t workpeople-server:verified .
```

Стадия `verify` устанавливает зависимости, проверяет типы, запускает модульные и
интеграционные тесты. Интеграционный тест поднимает временный gRPC-сервер внутри
контейнера и проверяет его остановку; внешние базы ему не обязательны. Установленные
на удалённом хосте Node.js и npm для этих проверок не требуются.

`sudo docker compose up -d --build` собирает конечный runtime-образ. BuildKit
пропускает независимую стадию `verify`; legacy builder может выполнить все
предшествующие стадии, включая тесты. В runtime-образ тесты и dev-зависимости
не попадают. Для проверки уже работающего Compose используйте
`sudo docker compose exec api node scripts/healthcheck.mjs`.

Для разработки исходников с автоматическим перезапуском установите Node.js 24 LTS
и npm на удалённом хосте и выполните там:

```sh
npm ci
sudo docker compose stop api
sudo docker compose -f compose.yaml -f compose.dev.yaml up -d postgres redis
npm run migration:run
npm run start:dev
```

Override публикует базы только на `127.0.0.1` удалённого хоста. При изменении `POSTGRES_PORT` или
`REDIS_PORT` обновите URL в серверном `.env`. Для контейнеров Compose автоматически
формирует URL с именами `postgres` и `redis`; `GRPC_PORT` из `.env` задаёт внешний
порт, а внутри контейнера API слушает порт 50051.

API запускается и без доступных баз, чтобы диагностировать соединения: состояние
будет `degraded`. Клиент показывает это отдельно от недоступного сервера.

## Команды

Все серверные команды ниже выполняются на `192.168.0.102` через SSH. Для `npm`
нужны Node.js и установленные зависимости при работе с исходниками; обычное
развёртывание и рекомендуемые проверки используют Docker.

| Команда | Назначение |
| --- | --- |
| `sudo docker build --target verify -t workpeople-server:verified .` | Типы и все серверные тесты в контейнере |
| `npm run start:dev` | Разработка с автоматическим перезапуском |
| `npm run typecheck` | Проверка типов |
| `npm test` | Тесты конфигурации и здоровья сервиса |
| `npm run test:integration` | Реальный gRPC-вызов и корректная остановка NestJS |
| `npm run build` | Компиляция в `dist` |
| `npm start` | Запуск скомпилированного сервера |
| `npm run healthcheck` | gRPC-проверка API и зависимостей |
| `npm run migration:run` | Применение SQL-миграций |

## Структура

```text
src/
  config/             проверка окружения
  infrastructure/     PostgreSQL и Redis
  modules/
    auth/             будущая авторизация
    employees/        будущие сотрудники
    departments/      будущие отделы
    health/           рабочий gRPC HealthService
proto/workpeople/v1/  канонические контракты
scripts/              миграции и probe
migrations/           SQL-миграции
```

Не добавляйте бизнес-логику в gRPC-контроллеры: контроллер вызывает сервис модуля,
сервис работает с репозиториями/инфраструктурой. Профили сотрудников и учётные записи
должны оставаться разными сущностями. [Подробная архитектура](docs/architecture.md).

## Контракт клиента

Сервер владеет `proto/workpeople/v1/health.proto`. В клиентском репозитории запустите:

```sh
npm run contracts:sync
```

Команда копирует контракты из соседней папки `work-peaple-server/proto`.
Для другого расположения передайте путь после `--`.
Обновлённая копия хранится в Git клиента; обе сборки остаются независимыми.
Несовместимые изменения API выпускайте новым пакетом protobuf (`workpeople.v2`).

## Удалённое подключение и TLS

Основной режим использует gRPC без TLS внутри SSH-туннеля, сохраняя
`GRPC_BIND_ADDRESS=127.0.0.1` на удалённом хосте. Для прямого доступа по сети задайте
`GRPC_BIND_ADDRESS=0.0.0.0` и включите TLS либо настройте TLS на gRPC-совместимом прокси.
Для TLS положите сертификат и ключ в `certs/server.crt` и `certs/server.key`,
установите `GRPC_TLS_ENABLED=true`. В Compose каталог `certs` доступен только для чтения.
Для собственного центра сертификации положите CA в `certs/ca.crt` и задайте
`GRPC_TLS_CA_PATH=./certs/ca.crt`. При сертификате на DNS-имя укажите его в
`GRPC_TLS_SERVER_NAME`, чтобы локальная проверка контейнера проверяла это имя.
Клиенту нужны адрес сервера, включённый TLS и при необходимости этот же публичный CA;
приватный ключ остаётся на сервере. Подтверждение сертификата не отключается.

Портам PostgreSQL и Redis не нужен публичный доступ. После изменения паролей
существующий том PostgreSQL сохраняет прежние учётные данные: измените пароль
пользователя SQL-командой и затем обновите окружение. `.env` и сертификаты исключены из Git.
