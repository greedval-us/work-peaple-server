# Проверка начального скелета

## Первичная локальная проверка — 2026-10-29

Проверено на Windows с Node.js 24.14.1 и npm 11.11.0.

- Сервер: `npm run typecheck`, `npm run build` — успешно.
- Сервер: `npm test` — 11 тестов, включая недоступные зависимости и контрольные суммы миграций LF/CRLF.
- Сервер: `npm run test:integration` — реальный скомпилированный NestJS, gRPC-запрос
  с зависимостями, принимающими TCP без ответа, ограниченное время ответа и корректная остановка.
- Клиент: `npm run build` — TypeScript, Vue и production-сборка успешно.
- Клиент: `npm test` — 11 тестов конфигурации, доверенных URL и реальных loopback gRPC-вызовов.
- Клиент: `npm run pack` — Windows x64, `release/win-unpacked/Work People.exe`.
- Проверен состав `app.asar`: main, sandbox preload, renderer и production-зависимости
  grpc-js/proto-loader/dotenv присутствуют; `.env` отсутствует; внешний proto совпадает с исходником.
- Собранный `.exe` запущен: при выключенном API показывает недоступный сервер,
  после запуска настоящего NestJS показывает соединение и состояние `degraded`
  с недоступными PostgreSQL и Redis.
- `npm run contracts:sync` — успешно, файлы контрактов клиента и сервера совпадают.
- YAML Compose и electron-builder разобран парсером; Git исключает зависимости,
  сборки и секреты и сохраняет примеры окружения и lock-файлы.
- Независимое ревью завершено без оставшихся существенных замечаний.

Docker CLI/Engine на этой машине отсутствует. `docker compose up --build`, живые
PostgreSQL/Redis, применение миграций к PostgreSQL и контейнерный healthcheck здесь
не запускались. Windows-установщики NSIS/portable имеют команды сборки, но в рамках
этой проверки собран и запущен распакованный пакет. TLS настраивается в обеих сторонах;
развёртывание с настоящими сертификатами требует отдельной проверки в целевой среде.

## Удалённое развёртывание на 192.168.0.102

После уточнения пользователя все последующие серверные запуски и проверки
выполнялись только на `greed@192.168.0.102` по SSH.

- Система: Ubuntu 26.04.1 LTS, Docker 29.1.3, Compose 2.40.3.
- Каталог: `/home/greed/apps/work-people-server`; Compose-проект: `workpeople`.
- Исходники переданы без node_modules, приватных ключей и локальных секретов;
  контрольная сумма архива проверена перед распаковкой.
- Серверный `.env` создан на удалённом хосте со случайными URL-safe паролями
  PostgreSQL/Redis и правами `0600`. Пароль SSH в файлы проекта не сохранялся.
- `sudo docker compose up -d --build --wait --wait-timeout 180` завершился успешно.
- API, PostgreSQL и Redis имеют статус `healthy`; сервис `migrate` завершился с кодом 0.
- `sudo docker compose exec -T api node scripts/healthcheck.mjs` вернул `status: ok`
  и состояния `postgres: up`, `redis: up`.
- `sudo docker build --target verify -t workpeople-server:verified .` завершился успешно:
  TypeScript, 11 модульных тестов и 1 реальный интеграционный gRPC-тест.
- Повторный `sudo docker compose run --rm --no-deps migrate` завершился без ошибок.
- Распакованный Windows-клиент подключился через SSH-forward
  `127.0.0.1:50051 → 192.168.0.102 → 127.0.0.1:50051` и показал доступные API и обе базы.
- gRPC опубликован только на loopback удалённого хоста; порты PostgreSQL/Redis
  остаются во внутренней сети Compose. Node.js на удалённую ОС не устанавливался:
  приложение и проверки работают в контейнерах.
- Существующий Compose-проект `ai-stack` сохранил работающие контейнеры.

На хосте нет buildx: для проверки применён совместимый `docker build --target verify`
без флага `--progress`. Compose самостоятельно собрал runtime-образ.
В новом развёртывании пока нет бизнес-миграций; выполнена подготовка таблицы истории
миграций. Прямой TLS с реальными сертификатами остаётся отдельной проверкой;
проверенное соединение защищает SSH-туннель.
