# Архитектура Work People

## Назначение и границы

Desktop-приложение для управления сотрудниками одной компании с несколькими отделами.
Два независимых Git-репозитория: Electron-клиент и NestJS-сервер.
Реализованы вход и серверная основа пользователей, ролей и прав. Desktop пока содержит
только вход и рабочее пространство; административные экраны и CRUD сотрудников появятся позже.
Сотрудник и учётная запись — разные сущности. Мультиарендность не нужна.

## Выбранный подход

Пользователь выбрал Electron + Vue 3 + TypeScript и NestJS + gRPC.
Рассматривался сервер на чистом Node.js + grpc-js: меньше зависимостей, но соглашения,
валидацию и внедрение зависимостей пришлось бы поддерживать самостоятельно.
NestJS выбран ради модулей и единых соглашений при дальнейшем расширении.
Сервер работает как модульный монолит и компилируется TypeScript: стандартные
декораторы NestJS требуют компиляции, поэтому нативное удаление типов Node здесь не применяется.

## Клиент

- `src/main`: жизненный цикл Electron, gRPC, конфигурация подключения и проверка отправителя IPC.
- `src/preload`: ограниченный API через contextBridge; произвольные IPC-каналы не доступны UI.
- `src/shared`: типы данных API между процессами.
- `src/renderer/src`: Vue Composition API; корневой компонент собирает оболочку и панель подключения.
- `proto`: копия серверного контракта, необходимая для независимой сборки.

Renderer работает с sandbox, contextIsolation и без nodeIntegration.
Серверные настройки и текущий токен сессии находятся в памяти main, а не в Vue.
Клиент не подключается напрямую к PostgreSQL или Redis.

## Сервер

- `src/modules/health`: gRPC-проверка состояния API, PostgreSQL и Redis.
- `src/modules/auth`: пароли, вход, сессии, общий guard и декораторы авторизации.
- `src/modules/access`: пользователи, роли, каталог прав и административные RPC.
- `src/modules/employees`, `departments`: границы будущих функциональных модулей.
- `src/infrastructure`: пул PostgreSQL и подключение Redis с закрытием при остановке.
- `src/config`: проверка окружения при старте.
- `migrations`, `scripts`: версионируемые миграции и служебные команды.

Направление зависимостей: транспорт → прикладной сервис → инфраструктура.
PostgreSQL — источник постоянных данных; Redis предназначен для временных данных и кеша.
Учётные записи находятся в `users`; таблицы сотрудников и отделов добавляются отдельно.

## Пользователи, роли и права

| Таблица | Назначение |
| --- | --- |
| `users` | UUID, уникальный нормализованный логин, хеш пароля, ФИО, email, телефон, активность, автор и временные метки |
| `roles` | Уникальный неизменяемый код, название, описание и признак системной роли |
| `permissions` | Каталог реализованных прав со стабильными кодами, ресурсом и описанием |
| `user_roles` | Несколько ролей на пользователя и сведения о назначении |
| `role_permissions` | Связь ролей с правами |
| `auth_sessions` | Отпечаток токена, пользователь, абсолютный срок и время отзыва |
| `bootstrap_state` | Постоянный маркер однократной инициализации |

Эффективные права — объединение прав всех ролей. Роль `admin` является системной
и получает полный каталог; скрытого условия по логину пользователя нет.
Новые функции добавляют права миграцией, а контроллеры явно указывают требуемые
коды через `@RequirePermissions`. Публичны только вход и технический healthcheck;
остальные RPC по умолчанию требуют действующую сессию.

Создание/изменение пользователей и ролей выполняется транзакционно с параметризованным
SQL. Изменения доступа сериализуются advisory lock и повторно проверяют права инициатора.
Проверка последнего активного администратора входит в ту же транзакцию: два
параллельных изменения не могут одновременно лишить систему всех администраторов.

Используются отзываемые серверные сессии вместо JWT с refresh-токенами: для текущего
desktop это уменьшает число механизмов и обеспечивает применение новых прав сразу.
Токен генерируется CSPRNG, в базе хранится SHA256. Main Electron хранит токен в памяти
до выхода/истечения срока/закрытия приложения; renderer получает только безопасный DTO.
Вход ограничен Redis по логину и общему бюджету; при недоступном ограничителе вход
завершается контролируемой ошибкой. Пароли хешируются асинхронным scrypt с солью
и ограниченным числом параллельных операций.

Начальный `admin/admin` создаётся после миграций под транзакционной блокировкой.
Маркер bootstrap не позволяет восстановить этот доступ после смены пароля или логина.
API не создаёт учётные записи при запуске и сохраняет диагностику при недоступной базе.

## Контракт и соединения

Канонические файлы: `proto/workpeople/v1/{health,identity,auth,access}.proto` в серверном репозитории.
Пакет protobuf: `workpeople.v1`. Метод `HealthService.Check` возвращает `status`, `service`,
`version`, `checkedAt`, `dependencies`. Состояния API: `ok`/`degraded`;
состояния зависимостей: `up`/`down`.
Команда клиента `npm run contracts:sync` обновляет отслеживаемую копию из соседнего сервера;
можно явно передать другой каталог proto. Обычные сборки соседний репозиторий не читают.
Поля protobuf нельзя перенумеровывать или переиспользовать; несовместимые изменения получают v2.

Серверный хост разработки и развёртывания — `192.168.0.102`, доступный по SSH
на стандартном порту 22. API, PostgreSQL, Redis, миграции и серверные интеграционные
тесты выполняются только на этом хосте. Локальный Windows используется для Electron-клиента.
Основное подключение — защищённый SSH-туннель:

```powershell
ssh -i "$HOME/.ssh/id_ed25519_hostkey" -p 22 -N -L 127.0.0.1:50051:127.0.0.1:50051 greed@192.168.0.102
```

Учётная запись удалённого хоста — `greed`; `-i` выбирает существующий
локальный ключ `~/.ssh/id_ed25519_hostkey`.
Приватный ключ остаётся на клиентском компьютере. Туннель позволяет сохранить
`GRPC_TARGET=127.0.0.1:50051` и `GRPC_TLS_ENABLED=false` у клиента и loopback-публикацию
gRPC в Compose. Для прямого подключения по сети включается проверяемый TLS на сервере
или gRPC-совместимом прокси. Защищённые методы получают Bearer-токен через gRPC metadata;
проверка ролей и прав всегда выполняется сервером.

## Docker

Compose запускается на `192.168.0.102` командами из SSH-сеанса и поднимает API,
одноразовый сервис миграций, PostgreSQL и Redis.
PostgreSQL и Redis доступны только внутри сети Compose; с хоста по умолчанию публикуется
только gRPC на `127.0.0.1:50051`. Есть healthchecks, постоянные именованные тома и restart policy.
API ждёт успешного завершения миграций и готовности зависимостей.
PostgreSQL 18 хранит данные в томе `/var/lib/postgresql`.
Отдельный override публикует порты баз только на loopback удалённого хоста для
разработки сервера с Node.js на этом же хосте.
Клиент устанавливается на рабочие компьютеры и не запускается внутри серверного Compose.

## Проверка и ограничения среды

Проверяем TypeScript, сборки, тесты валидации конфигурации и health-сервиса,
реальный gRPC-вызов без обязательных внешних баз и состав установочного пакета клиента.
Серверные проверки выполняются по SSH на `192.168.0.102`; Compose требует Docker Engine/Compose
на этом хосте. Клиентские проверки и сборки выполняются на Windows; изолированный
loopback gRPC в тестах клиента не требует развёртывания серверных компонентов на Windows.
Секреты, базы, node_modules, сборки, установщики и локальные настройки исключаются из Git;
lock-файлы и `.env.example` хранятся в репозитории.
